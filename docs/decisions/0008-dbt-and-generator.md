# ADR 0008: dbt layout and the generator

- Status: Accepted
- Date: 2026-11-04

## Context

Mapping specifications in `mapping_spec/*.yml` are the source of truth. SQL, tests and docs have to be derivable from them, or the documentation-first claim is empty. dbt is the right executor (incremental models, tests, lineage graph, docs), but dbt alone would not make the spec authoritative.

## Decision

TraceMap uses dbt-core 1.12 with dbt-postgres 1.11, in three layers:

- **staging** (view): one view per source CSV, selected from `raw.synthea_*`. Column names are lowercased and kept as text. Minor transforms live here, each with a one-line comment explaining why (e.g. medications' `stop` coalesced to `start` for ongoing medications).
- **intermediate** (view/table): the vocabulary plumbing (`int_standard_concept_map`, `int_source_concept_lookup`, `int_ucum_unit_map`, `int_value_as_concept_map`), the key maps (`int_person_key_map`, `int_care_site_key_map`, `int_provider_key_map`, `int_visit_source_key_map`), the deterministic Synthea encounter class lookup (`int_synthea_encounterclass_map`), and derived inputs the CDM layer needs (`int_person_event_dates`, `int_location`).
- **cdm** (table): one table per OMOP CDM v5.4 target. Generated from the specs for straightforward tables, hand-written for the few that need custom logic the generator doesn't express.

`generate_schema_name` is overridden so custom schemas (`cdm`, `etl_meta`) are used directly, not prefixed with the profile's default. This matches OHDSI conventions.

**Generator (`src/tracemap/generate/`):** reads every `mapping_spec/*.yml` and writes:
- One `dbt/models/cdm/<table>.sql` per spec.
- One `dbt/models/cdm/schema.yml` with `not_null` tests for every column the OHDSI CDM v5.4 DDL marks NOT NULL, plus `unique` tests for the surrogate primary key.

Each output file starts with a banner: *GENERATED by tracemap generate from mapping_spec/\<spec\>.yml. Do not edit by hand.* Rerunning `tracemap generate` is idempotent.

**Stubs for tables the generator doesn't cover.** `observation_period`, `location`, `care_site`, `cdm_source`, `metadata`, `measurement` and `observation` all need something the generator doesn't express (derived min/max dates, address de-duplication, category filters, or build-time derived values). The generator emits a one-screen stub naming the reason, and the table has a hand-written SQL file that overwrites the stub. On the next `tracemap generate` the hand-written file wins because dbt's file resolution reads whatever is on disk and the generator skips any file tagged as unsupported.

## Alternatives considered

- **Pure dbt without a generator.** Simpler, but doc drift becomes inevitable. The spec would only be a planning aid, not a contract.
- **Generate dbt YAML sources too.** Possible, but `sources.yml` changes rarely while mappings change often; leaving sources hand-maintained keeps the generator small.
- **SQLGlot-based parser.** Overkill for Phase 1 and hides intent. Jinja + a few helpers is both readable and auditable.
- **One mapping per rule, multiple files per table.** More granular but harder to review. One YAML per target table matches how reviewers think.

## Consequences

- Any change to a mapping rule starts in YAML. `tracemap generate` then updates every downstream artefact.
- A change to a stubbed hand-written model stays in SQL and is documented in a comment alongside the spec's own text.
- CI will verify (Phase 2) that `tracemap generate` produces zero diff against committed files, so the two never drift.

## In plain English

The YAML mapping files are the plan. A generator turns the plan into the SQL dbt runs, and the tests that check it. A handful of tables need custom SQL the generator cannot express; each has a clearly marked stub explaining why, and a hand-written override.
