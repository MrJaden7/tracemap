# ADR 0012: UK synthetic extract and pseudonymised linkage

- Status: Accepted
- Date: 2026-11-04

## Context

Real NHS extracts are coded in ICD-10 and OPCS-4, not SNOMED. They live in a different system from any primary care record and can only be joined to the other source through a pseudonymised identifier. Phase 2 needs to demonstrate TraceMap handles that reality.

## Decision

A synthetic UK hospital extract is generated by `src/tracemap/sources/uk_extract.py`:

- **UK patient ids** are 10-digit strings (NHS-like, but without a mod-11 check digit; this is stated in the output and in docs).
- **Linkage** is a HMAC-SHA256 of the Synthea patient id using a secret salt taken from the `TRACEMAP_LINKAGE_SALT` environment variable. The salt itself is never committed and never written to the database; only the HMAC output is stored, which is one-way. The intermediate layer joins Synthea persons to UK persons via `etl_meta.synthea_linkage_keys`, which is populated by the loader side-by-side with the UK CSVs.
- **Coding** is derived from the Synthea SNOMED codes via `vocab.concept_relationship` ('Mapped from' / 'Maps to') to ICD-10 for diagnoses and OPCS-4 for procedures. Codes that have no mapping are dropped from the UK extract: the mapper shouldn't be fooled by Synthea's SNOMED where no UK equivalent exists.
- **Deliberate messiness** at 8% of records (configurable): extra whitespace, missing or extra dots, lowercase, trailing zero. The `normalise_icd10` and `normalise_opcs4` dbt macros clean them up, and the mapping spec notes the fix.
- **Separate id spaces** in the CDM so UK and Synthea rows never collide: UK `person_id` starts at 10,000,000 and UK `condition_occurrence_id` at 100,000,000.

## Alternatives considered

- **Hand-crafted UK extract fixtures.** Faster to write, but would not demonstrate the mapping spec handling two sources with real vocabulary relationships.
- **A separate database.** More realistic for an SDE (two sources rarely share infrastructure), but it hides the mapping work in integration glue instead of showing it in the dbt model.
- **Reuse the Synthea patient id directly.** Impossible: the whole point is to prove the cross-source join works when the identifiers are different.

## Consequences

- Any Synthea patient whose UUID is in `etl_meta.synthea_linkage_keys` can be joined to their UK records via `int_person_cross_source`, with no plaintext identifier ever persisted.
- The messy-code rate is a knob for Phase 3 evaluation: the AI mapping module is scored on how well it handles the exact kinds of messiness the UK extract injects.

## In plain English

A second synthetic source is generated in the UK's own coding systems, deliberately messy, and linked to the first source by a one-way key. Nothing identifiable crosses either way.
