# ADR 0010: Row lineage and the trace command

- Status: Accepted
- Date: 2026-11-04

## Context

Row-level provenance is the project's most-persuasive demonstration of correctness. The hiring panel should be able to pick a CDM row and see its exact source. The raw loader (ADR 0007) stores `_source_row` and `_run_id` on every raw row, plus a SHA-256 for every file in `raw.load_manifest`. This ADR says how the trace command walks from one to the other.

## Decision

Two row shapes exist and the `TRACES` dictionary in `src/tracemap/lineage/trace.py` names them:

1. **Direct** (event tables): the CDM row's surrogate id IS `_source_row`. This holds for `visit_occurrence`, `condition_occurrence`, `drug_exposure`, `procedure_occurrence`, `measurement` and `observation`, all of which assign their id as `cast(_source_row as int)` in the generated SQL.

2. **Key-map** (person, care_site, provider, location): the CDM row's id is generated by an intermediate model (`int_*_key_map`) with `row_number()` over `_source_row`. The key map records the source row, so `trace` queries the key map to find it, then looks up the raw row.

`tracemap trace <cdm_table> <id>` prints:
- the CDM row's columns;
- the source table, row number and run id;
- the file name, SHA-256 and local path from `raw.load_manifest`;
- the matching raw row.

Non-traceable tables (observation_period, cdm_source, metadata) are derived at build time rather than from a single source row, and are refused by the command with an error naming the traceable options.

## Alternatives considered

- **Materialise `etl_meta.row_lineage` with (cdm_table, cdm_id, source_table, source_row, run_id).** More queryable, but duplicates data already present on raw rows. Phase 2 may add a materialised view of this join for dashboards; Phase 1 queries live.
- **Encode lineage in a JSONB column on every CDM row.** Pollutes the CDM schema and would fail dbt tests against the OHDSI DDL.
- **Query only by UUID.** Works for person, but not for event tables where the natural key is the row's position in the source file.

## Consequences

- One hand-curated dictionary (`TRACES`) must be kept in step with generated models. A unit test asserts that every entry has a coherent shape; a Phase 2 integration test will round-trip real ids.
- Non-event tables have to document their build-time derivation in their stub SQL file, which they already do.

## In plain English

Any CDM row can be traced back to the exact line in the exact CSV it came from, with a checksum of that file and the run that loaded it. Two shapes are needed because some ids are the file row number directly, and some are generated from it.
